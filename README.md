# Native PostgreSQL 2PC across microservices

This is a runnable money-transfer demo with three independent PostgreSQL databases:

```text
client
  |
  v
Coordinator (:3000, coordinator-db)
  |                         durable decision log
  +---- prepare / commit ----> bank-a (:3001, bank-a-db)  debit Alice
  |
  +---- prepare / commit ----> bank-b (:3002, bank-b-db)  credit Bob
```

The coordinator generates one transaction ID per transfer and persists the participants, decision, and progress in its own database. Each participant owns its account table and PostgreSQL instance. No database is shared between services.

## Important implementation note

Prisma is used for database schema/client work and for the coordinator's durable log. The actual `BEGIN` → business update → `PREPARE TRANSACTION` sequence uses one checked-out `pg` client. That is deliberate: 2PC requires every statement in phase 1 to execute on the exact same database connection. Calling ordinary Prisma methods followed by `$executeRaw('PREPARE TRANSACTION ...')` cannot safely guarantee that connection affinity, because Prisma normally pools each query independently.

The participant code still demonstrates the native PostgreSQL commands directly:

```sql
PREPARE TRANSACTION 'coordinator-generated-id';
COMMIT PREPARED 'coordinator-generated-id';
ROLLBACK PREPARED 'coordinator-generated-id';
```

Transaction identifiers are UUIDs generated by the coordinator and validated before being inserted into the non-parameterizable PostgreSQL prepared-transaction statements.

## Run it

Prerequisites: Docker Desktop with Compose enabled.

```powershell
docker compose up --build
```

Wait until all three HTTP services report that they are listening. The compose file starts each participant database with `max_prepared_transactions=100`; a normal PostgreSQL default of `0` would reject phase 1.

In a second PowerShell window, check the initial state:

```powershell
Invoke-RestMethod http://localhost:3001/accounts
Invoke-RestMethod http://localhost:3002/accounts
```

Initial balances are Alice at Bank A = `100000` cents and Bob at Bank B = `50000` cents.

### Successful commit

```powershell
$body = @{ amountCents = 2500 } | ConvertTo-Json
Invoke-RestMethod -Method Post http://localhost:3000/transfers -ContentType 'application/json' -Body $body
Invoke-RestMethod http://localhost:3001/accounts
Invoke-RestMethod http://localhost:3002/accounts
```

The result is a completed `COMMIT`; balances become `97500` and `52500`.

### Forced abort

This injects a phase-1 failure at Bank B. Bank A may already be prepared, but the durable decision becomes `ABORT` and both participants receive `ROLLBACK PREPARED`.

```powershell
$body = @{ amountCents = 1250; forcePrepareFailureAt = 'bank-b' } | ConvertTo-Json
Invoke-RestMethod -Method Post http://localhost:3000/transfers -ContentType 'application/json' -Body $body
```

Both balances remain unchanged by this request.

### Coordinator crash recovery

This deliberately exits the coordinator *after* it durably writes the decision and *before* phase 2. Docker restarts it (`restart: on-failure`), and startup recovery replays that decision to every participant.

```powershell
$body = @{ amountCents = 700; simulateCrashAfterDecision = $true } | ConvertTo-Json
Invoke-RestMethod -Method Post http://localhost:3000/transfers -ContentType 'application/json' -Body $body
docker compose logs -f coordinator
```

The request may return `202`, or the deliberate exit can cut the connection first. In either case, wait a moment, then inspect the result:

```powershell
Invoke-RestMethod http://localhost:3000/transactions
Invoke-RestMethod http://localhost:3001/accounts
Invoke-RestMethod http://localhost:3002/accounts
```

The transaction has a durable `COMMIT` decision and ultimately reaches `COMPLETED` after restart.

## Inspecting state

HTTP views:

```powershell
Invoke-RestMethod http://localhost:3000/transactions       # coordinator decision log
Invoke-RestMethod http://localhost:3001/prepared           # Bank A's pg_prepared_xacts
Invoke-RestMethod http://localhost:3002/prepared           # Bank B's pg_prepared_xacts
```

Or see the physical decision log directly:

```powershell
docker compose exec coordinator-db psql -U coordinator -d coordinator -c 'TABLE "DistributedTransaction";'
```

The `participants` JSON contains phase progress (`prepared`, `committed`, `rolled_back`, etc.); `decision` is the durable source of truth for recovery.

## Demonstrating locks and blocking

A prepared transaction retains its locks. Prepare a debit directly, then leave it unresolved:

```powershell
$gid = 'lock-demo-001'
$body = @{ transactionId = $gid; operation = @{ kind = 'debit'; accountId = 'alice'; amountCents = 100 } } | ConvertTo-Json -Depth 4
Invoke-RestMethod -Method Post http://localhost:3001/prepare -ContentType 'application/json' -Body $body
Invoke-RestMethod http://localhost:3001/prepared
```

At this point another prepare/update of Alice will block on the row lock (or hit its HTTP timeout). Resolve it to release the lock:

```powershell
Invoke-RestMethod -Method Post http://localhost:3001/rollback -ContentType 'application/json' -Body (@{ transactionId = $gid } | ConvertTo-Json)
```

This endpoint is intentionally unauthenticated because it is a local protocol demo. In a real deployment, participant phase endpoints must be mutually authenticated and only callable by the coordinator.

## Advanced Enterprise Optimizations & Resilience

### 1. Read-Only / One-Phase Commit (1PC) Optimization
In classic enterprise transaction managers (Tuxedo, XA, Narayana), participants that only perform read operations, balance inquiries, or have zero balance delta vote `VOTE_READ_ONLY` in Phase 1.
- **Phase-2 Dismissal:** The coordinator immediately marks that participant as `read_only` and dismisses them from Phase 2.
- **Zero Lock Contention:** The participant executes read validation without `FOR UPDATE` and completely skips `PREPARE TRANSACTION`, leaving no prepared locks in PostgreSQL.
- **50% Network Round-Trip Reduction:** Cuts Phase-2 message overhead entirely for read-only participants.

### 2. Chaos Monkey / Network Partition & Latency Injector
A built-in fault-injection interceptor allows testing distributed networking degradation:
- **Packet Drops (`action: "drop"`):** Simulates lost messages between coordinator and participants in Phase 1 or Phase 2.
- **Injected Latency (`action: "delay"`):** Delays outgoing requests by configurable milliseconds (e.g. 3500ms) to test socket timeouts and client aborts.
- **Network Partitions (`action: "partition"`):** Simulates split-brain and unreachable services.
- **Cluster Self-Healing:** Proves that transient Phase-2 drops (e.g. `times: 1`) leave transactions in `DECIDED`, which the automated recovery worker (`/recovery/run`) subsequently replays and heals to `COMPLETED`.

## Failure semantics and operational limits

1. **Before a decision:** A coordinator crash can leave a transaction in `PREPARING`. An automated background reaper sweeps every 60s (configurable) and automatically aborts transactions stuck in `PREPARING`, rolling back prepared participants to release database locks. An operator can also manually trigger abort via `/transactions/:id/abort` or `/reaper/run`.
2. **After a decision:** Recovery is deterministic. The coordinator only replays its persisted `COMMIT` or `ABORT`, at startup and every 10 seconds until all participant calls acknowledge.
3. **Idempotency keys:** Clients can pass an `Idempotency-Key` HTTP header to `POST /transfers`. Duplicate requests return the original transaction response and prevent double debits/credits. Mismatched request parameters for an existing key return `422 Unprocessable Entity`.
4. **Multi-currency 3-participant 2PC:** Cross-currency transfers (USD -> EUR) coordinate three 2PC participants in atomic lock-step: Bank A debits USD, Rates Service locks the exchange rate quote, and Bank B credits the converted EUR. If any participant fails, all prepared participants are rolled back.
5. **Read-only participants:** Participants voting `VOTE_READ_ONLY` hold no `pg_prepared_xacts` and receive zero Phase-2 calls, releasing participant resources immediately.
6. **Network degradation & Chaos Monkey:** Simulated latency exceeding `participantTimeoutMs` or dropped Phase-1 packets trigger automatic rollback of prepared participants. Dropped Phase-2 packets are safely recovered by the crash recovery worker.
7. **Participant response timeout:** A timeout in phase 1 causes a durable `ABORT`. A timeout in phase 2 leaves the decision log in `DECIDED`, and recovery retries it. Network uncertainty means a participant can have prepared even when its response was lost, which is why abort is sent to every participant.
8. **Idempotent resolution:** A participant treats a missing GID as `not_found`, so repeated phase-2 delivery is safe for this demo. Production systems normally add reconciliation/audit records and alerting for a missing expected GID, because absence alone cannot prove whether a human or prior resolver committed or rolled it back.
9. **2PC cost:** Prepared transactions hold locks and consume PostgreSQL resources. They should be monitored (`pg_prepared_xacts`), time-bounded operationally, and kept very short. A Saga trades global atomicity for local commits plus compensating actions, usually giving higher availability for long-running workflows.

## Resetting the demo

To erase all databases and return to the initial balances:

```powershell
docker compose down -v
docker compose up --build
```

`down -v` removes the named Docker volumes created by this demo.
